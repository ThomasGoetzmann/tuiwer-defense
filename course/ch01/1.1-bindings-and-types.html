In F#, let is also immutable and let mutable is the exception. Rust made the same choice.

Concept

Mutation is visible

In Rust, you can see every place that changes a value. Look for mut. If a binding has no mut, its value does not change. This is a big help when you read code, and it is the base for the borrowing rules in chapter 3.

let lives = 20;            // immutable
let mut gold = 100;        // mutable: the reader is warned
gold -= 30;

let input = "42";          // &str
let input: u32 = input.parse().unwrap();   // shadowing: same name, new type
// the old `input` is hidden, not changed

Shadowing is not mutation. It creates a new variable. Use it when a value changes form, like text that becomes a number. .unwrap() means “crash if this failed”. Chapter 4 replaces it.

Integer types

SignedUnsignedUse in this game
i8 … i128u8 … u128u32 for gold, lives, damage. They are never negative.
isizeusizeusize for indexes into lists.
f32, f64Avoid in game rules. Floats make tests and replays harder.

An unsigned type makes a whole class of bugs impossible: gold can never be −5. But you must handle the edges. What is 3 - 5 for a u32?

Hands-on

Explore in a test

  1. Add this test to the tests module in tuiwer-domain/src/lib.rs. Run it with cargo test --workspace.

    Always add --workspace (or -p tuiwer-domain). Without it, cargo uses default-members and tests only the TUI crate.

    #[test]
fn explore_unsigned_edges() {
    let small: u32 = 3;
    println!("checked:    {:?}", small.checked_sub(5));
    println!("saturating: {}", small.saturating_sub(5));
    println!("wrapping:   {}", small.wrapping_sub(5));
    println!("plain:      {}", small - 5);
}

    It does not even compile. Read the error: the compiler knows that small is 3, so it sees the overflow before the program runs.

  2. Hide the value from the compiler. Change the first line, then run the test again:

    let small: u32 = std::hint::black_box(3);

    black_box stops the compiler from knowing the value. Now the test compiles and fails at run time. Read the panic message.

  3. Tests hide println! output when they pass. To see it, remove the last line and run:

    cargo test --workspace -- --nocapture

  4. Put the last line back. Now run the test in release mode:

    cargo test --workspace --release -- --nocapture

    No panic: the value wraps around silently. Debug builds check overflow, release builds do not. So never trust plain - at an edge. Say what you want.

  5. Delete the exploration test before you commit.
Exercise 1.1-A

Add two constants and one game rule to the domain crate:

  • STARTING_GOLD is 100 and STARTING_LIVES is 20. Both are public u32 constants.
  • damage_after_armor(damage, armor) takes two u32 values. Armor reduces the damage. A hit always does at least 1 damage.

Write the tests first. Make them fail, then pass:

#[test]
fn armor_reduces_damage() {
    assert_eq!(damage_after_armor(10, 3), 7);
}

#[test]
fn zero_armor_keeps_damage() {
    assert_eq!(damage_after_armor(4, 0), 4);
}

#[test]
fn a_hit_always_does_at_least_one_damage() {
    assert_eq!(damage_after_armor(2, 5), 1);
    assert_eq!(damage_after_armor(0, 0), 1);
}

#[test]
fn starting_values() {
    assert_eq!(STARTING_GOLD, 100);
    assert_eq!(STARTING_LIVES, 20);
}

Use this signature. The body is yours:

pub fn damage_after_armor(damage: u32, armor: u32) -> u32
Hint 1: direction

What happens when armor is larger than damage? Your explore test gave the answer.

Hint 2: concept

Integer types have methods. Look at u32 in rustup doc --std. You need one method that stops at zero, and one method that gives the larger of two values. Methods can be chained.

Hint 3: almost code

saturating_sub and max. The body is one expression, without return and without ;.

Compiler error of the day

Add this to a test, then read both errors:

let lives: u32 = 20;
let leaked: i32 = 3;
let left = lives - leaked;     // error 1
let tiny: u8 = 255 + 1;        // error 2
  1. You get E0308 mismatched types and E0277 cannot subtract i32 from u32. Rust never mixes u32 and i32, and - is defined only for two values of the same type. The help line suggests a conversion. Is it safe here?
  2. The second line shows no error yet. The compiler reports type errors first. Make leaked a u32, build again, and read the next error. It is a lint at compile time: the compiler sees the overflow before the program runs, as in the hands-on.
Boss fight

Write lives_after_leak(lives: u32, leaked: u32) -> u32. Then write gold_after_reward(gold: u32, reward: u32) -> u32. It must never overflow, even with u32::MAX. Write the edge-case tests first. Ask yourself: is saturating the right rule for gold, or is it a bug that should be visible? There is no single correct answer. Write your reason in a comment.

Why Rust does this

Implicit numeric conversions caused many real bugs in C and C++: a negative int becomes a huge unsigned, and a bounds check passes when it must fail. Rust removed all implicit conversions. It is more typing, but each conversion is a visible decision. For the same reason, debug builds check overflow: you find the bug in tests, not in production.

Deep dive

The type of an integer literal comes from how you use it. let x = 5; becomes i32 only if nothing else decides. If you later pass x to a function that takes u8, the literal becomes u8. Inference works on the whole function, not only on one line like C# var. You can also write a suffix: 5u8, 1_000_000u64. The _ is only for reading.
